# Software Engineering: Requirements Analysis (Final)

| No. | Requirement | Details |
| :-: | :--- | :--- |
| 1 | Once a new game round starts, the system must select a random geographical location from a list of valid land locations. | A round begins with the provision of the location and ends upon a final guess submission, the last available guess attempt, or expiration of the time limit. A valid location must meet the following conditions: be located on a land area; have the required weather data available; support the data sources required for the selected game mode. Location selection is random, though specific selection rules may be applied—for example, to prevent geographically close locations from appearing directly after one another. |
| 2 | While a game round is in progress and the player has selected a location, the system must allow the player to submit their guess either as a single attempt or as a final guess. | Submission is done via "Submit Guess" (single attempt) or "Final Submit." Each submitted guess uses one attempt; the number of available attempts depends on the difficulty level (see Requirement 5). After a single attempt, the actual location and score are not yet displayed. Multiple attempts act as multiple bets in the round: upon final submission, after the last available attempt, or upon timeout, the round ends and the player's **closest submitted attempt (Best-of-N)** is evaluated. Using "Final Submit" locks in immediately without requiring remaining attempts; after final submission, guesses can no longer be changed. |
| 3 | The system must be able to retrieve the required weather data for each selected target location via an external weather API. | The weather data required for the MVP includes: temperature, precipitation, humidity, and wind speed. The timestamp of the retrieved weather data must be no older than 120 minutes at the time of display. The API must provide corresponding data for the selected geographical coordinates. |
| 4 | As long as the game round has not ended, the system must conceal the actual location. | The actual coordinates and name of the target location must not be transmitted to the client before the round ends. This information must be stored and processed server-side. Only after the final evaluation may the server transmit the actual location information to the client. |
| 5 | As long as no round has been started, the system should offer the player the option to choose between the "Easy," "Medium," and "Hard" difficulty levels. | **Easy:** 7-minute time limit, selection from 6 predefined locations, 3 attempts, additional data available for free. **Medium:** 4-minute time limit, location selection via an interactive map with country borders, 2 attempts, unlocking additional data for 100 points. **Hard:** 2-minute time limit, location selection via an interactive map with country borders, 1 attempt, unlocking additional data for a 20-second time penalty. Additional data includes, for example, further weather metrics or hints about the location. |
| 6 | Once a game round has started, the system must display the core weather data retrieved for the target location (temperature, precipitation, humidity, wind speed), including units of measurement. | — |
| 7 | While a game round is in progress, the system must allow the player to select a geographical location as a guess for the target location. | The method of selection (list or interactive world map) depends on the difficulty level according to Requirement 5. |
| 8 | While a game round is in progress and the time limit has not expired, the system must allow the player to change the currently selected location as often as desired without consuming a guess attempt. | Location selection is performed by clicking on the map or selecting from a list. If the time limit expires, the player's **closest submitted guess (Best-of-N)** is automatically evaluated as the final guess. If no guess has been submitted yet, the most recently selected location is evaluated instead. If neither a guess was submitted nor a location selected, the score is 0. |
| 9 | Once a game round ends due to a final guess submission, the last available guess attempt, or expiration of the time limit, the system must calculate the geographical distance between the evaluated guess and the actual location, provided an evaluated guess exists. | The distance is calculated based on geographical latitude and longitude using the Haversine formula. The result is displayed in kilometers rounded to one decimal place. |
| 10 | Once the geographical distance has been calculated, the system must compute the player's score using a defined scoring formula. | **Value range:** The score per round is an integer from 0 to 5000. **Boundary values:** For a distance of up to 100 km (rounded per Requirement 9), the score is 5000. For a distance of at least 20,000 km, it is 0. **Monotonicity:** A smaller distance results in an equal or higher score. **Difficulty level:** The scoring rule may vary by difficulty level; the value range and boundary values apply across all difficulty levels. **Fairness:** Within a difficulty level, the same scoring rule applies to all players. **Deductions:** Point deductions (e.g., for additional data per Requirement 5) reduce the score to a minimum of 0. |
| 11 | Once a game round ends due to a final guess submission, the last available guess attempt, or expiration of the time limit, the system must display the actual location. | The actual location is shown with its place name or as a marker on the map. The player's evaluated (closest) guess and any other submitted attempts are displayed simultaneously. |
| 12 | The system must make the next round playable within 2 seconds of the player choosing **Next round** in singleplayer. | The system may fetch and cache the required location and weather data in advance. Weather failures under Requirement 13 are excluded from this timing requirement. |
| 13 | If the weather API fails to deliver all required weather data for a selected location within 3 seconds, the system must discard that location and select a new valid location. | A location is considered invalid if the weather data cannot be fully retrieved within 3 seconds or if at least one of the four required weather metrics is missing. Each selected location counts as one retrieval attempt. The system may fetch a maximum of three locations per game round. If all three retrieval attempts fail, the system must abort the game start and display a clear error message. |
| 14 | The system should allow the player to start an interactive tutorial from the main menu that explains the basic game mechanics. | The tutorial should cover: interpreting weather data, selecting a location on the map or from the selection list, submitting a guess, and calculating distance and score. It should be possible to exit, skip, and restart the tutorial at any time. |
| 15 | The system must display the core weather data consistently and responsively across all game rounds. | The weather data must be displayed in every round with consistent labels and units of measurement: °C (temperature), mm (precipitation), % (humidity), m/s (wind speed). The order of the weather information must remain consistent across all supported screen sizes. All information must be readable without overlapping or truncated content. |
| 16 | The system should allow multiple players to join a shared game lobby and play the same game rounds against each other. | All participants receive the same locations and use the difficulty set by the lobby creator. During play, the HUD shows the player's own score. Once all players have finished or timed out, the server reveals the target, guesses, round scores, and shared leaderboard sorted by total score. Players share a twenty-second review countdown. The server prepares the next round during review and starts it for everyone with the full time limit when the countdown ends and the round is ready. After the final review, the final standings remain visible on the match-complete screen. |
| 17 | The system must make the web application accessible without additional local installation via a public HTTPS URL in the two latest stable major versions of Chrome, Firefox, Safari, and Edge. | All application features are available without restriction in the specified browsers. |
| 18 | Once a game round is completed, the system should store the game results in a database for 6 months. | Game results include the achieved scores as well as the coordinates of the actual location and the evaluated guess (closest submitted attempt, or the last selected location on a zero-attempt timeout; null if none). Results are associated with the player's user account and automatically deleted after 6 months (data privacy). |
| 19 | The system must manage and use secret API keys for external interfaces exclusively on the server side. | API keys must not be stored in the public Git repository, included in frontend source code, bundled in the delivered client bundle, or exposed to the client via public API responses. Storage is handled via server-side environment variables or a suitable secret manager. |
| 20 | The system must encapsulate the user interface and core game logic in separate software modules. | The user interface and domain game logic must be clearly separated. Individual modules must be independently testable and maintainable. |

## Revision Notes

- **R12 & R16 (refined from [requirements_initial.md](requirements_initial.md)):** In singleplayer, players inspect their round results before advancing, so R12 was clarified to measure the 2-second loading limit from choosing **Next round** rather than forcing immediate auto-advance. R16 was expanded to specify synchronized multiplayer pacing (private HUD during play, shared reveal after everyone finishes/times out, a shared 20-second review countdown, server-side preparation so everyone starts the next round together with the full timer, and persistent final standings).
- **R2, R8, R11 & R18 (unified after playtesting):** Because intermediate attempts reveal neither score nor target (R2), discarding earlier guesses made multiple attempts meaningless. Evaluation was unified around **Best-of-N (multiple bets)** across explicit finalization, attempt exhaustion, and timeout (R2/R8), with all submitted attempts shown on reveal (R11) and the evaluated guess archived alongside its matching distance and score (R18).
